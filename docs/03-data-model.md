# 03 — Data model

MySQL 8, utf8mb4, UTC datetimes, CHAR(36) UUID primary keys.


Conventions: every table `id CHAR(36) PK`, `created_at DATETIME(3)`, `updated_at DATETIME(3)` unless noted. FK columns `*_id`. Enums as `VARCHAR(16)` with app-level enums (easier migrations than MySQL ENUM). Indexes listed are the non-trivial ones; all FKs get an index.

Score storage: `number` as decimal (3 places), `time` as total milliseconds in the same column. Ranking order: `score` by the leaderboard's `sort_order`, then `updated_at ASC, id ASC` (first to reach a score ranks higher). The same order is used for both list and rank so they agree (carrefour's mismatch avoided).

**Encrypted columns**: personal data that is not needed for querying is encrypted at rest with `apps/api/src/app/utils/Crypt.ts` (AES-256-CBC + HMAC under `APP_KEY`, same payload format as the express boilerplate) through a TypeORM column transformer. Where a lookup is still needed, a keyed blind index column (`<col>_hash`, HMAC of the normalised value) sits beside it and carries the unique constraint; `User.findByEmail()` is the only way to find an account by address. Today: `users.email`. Rotating `APP_KEY` is a data migration.

**Score history semantics**: `old_score` = previous all-time value (NULL if none), `new_score` = entered value (NULL = cleared), `year`/`month` = the period written. `PUT score` with a value equal to the current monthly, yearly and all-time values is a no-op (no row touch, no history row) so `updated_at` tie-breaks are not disturbed.

**ON DELETE rules**: child rows CASCADE from their parent (`group_members`, `group_invites`, `activities`, `activity_interests`, `activity_occurrences`, `occurrence_participants`, `leaderboards`, `leaderboard_*`, `calendar_sources`, `calendar_events`, and per-user data such as `refresh_tokens`, `calendar_*`, `manual_unavailability`, `weekly_unavailability_rules`, `push_subscriptions`). Actor references (`created_by_id`, `added_by_id`, `planned_by_id`, `updated_by_id`, `changed_by_id`, `invited_by_id`, `leaderboard_members.user_id`) are nullable with SET NULL, and the service fills the `*_name_snapshot` before the user row is deleted. Account-deletion order: snapshot names → leave every group (rules of 1.6) → revoke calendar tokens at the provider → delete user row (cascades the rest).
