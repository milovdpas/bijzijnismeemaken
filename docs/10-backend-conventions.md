# 10 — Backend conventions (apps/api)

Carried over from `C:\Users\milov\PersonalProjects\dynamic_alarm\apps\api` (its `docs/CONVENTIONS.md` is the longer prose version). The API skeleton is **copied** from that project and trimmed, see [02-architecture.md](02-architecture.md) section 2.3. It is not rewritten.

## Process and structure
- `src/app.ts` exports `createApp()` without listening so tests can mount it. `src/index.ts` connects the database first, then listens, and handles SIGTERM/SIGINT with a graceful shutdown (close server, then close DB, 20 s unref'd timeout).
- `GET /api/v1/health` runs a real `SELECT 1` with a timeout and answers 503 when the database is unreachable. The Docker `HEALTHCHECK` probes `127.0.0.1`, not `localhost`.
- Folders: `app/routes/groups/<resource>.ts` (route classes), `app/controllers`, `app/services`, `app/models/*.entity.ts`, `app/middleware`, `app/validators/*Schemas.ts`, `app/modules` (external providers), `app/utils`, `config`, `database/{migrations,typeorm-db,knexfile}`, `tools` (migrate, worker), `tests` (flat `*.test.ts` plus `support/`).

## Routing, controllers, services
- Class fields (static flags, injected services, constants) go at the top of a controller or service, before any handler or method.
- Do not extract a private helper that has one caller. Keep the code inside the handler or method that uses it; a helper earns its place only when a second caller appears.
- Each resource group is a class implementing `IRoute { getRoutes(): Router }`. It owns one controller instance (controllers are instantiated because their handlers are arrow properties; services are not) and declares each route on one line: path constant from `API_ENDPOINTS` (absolute paths, mounted at root), auth middleware, rate limit, `validate({ params, query, body })`, controller handler. Literal paths come before `:id` paths; use `router.get<IdParams>(...)` for typed params.
- A handler reads what it needs out of `req.body`, `queryOf()` and `paramsOf()` by destructuring at the top, then passes those named values to the service. Never hand `req.body` (or any request object) through to a service, even though validation already shaped it: the call site should show exactly which fields the operation uses. Controllers hold no module-level helper functions: a fact about one row is an entity method (`group.inviteLink()`), and a response that composes a row with other data is a presenter.
- Controllers have no private methods either, shared or not (no `respond`, `load` or `managed`). Each handler does its own lookups and its own response handling, even when several handlers answer the same way, so one handler reads top to bottom.
- Controllers are classes with arrow-property handlers typed `Handler<BodyOf<typeof schema>, Params>`. There is no async wrapper because Express 5 forwards rejected promises to the error middleware.
- `sendSuccess<T>(res, dto)` requires an explicit DTO type from `@bzim/types`. Lists are bare arrays; paginated lists use `{ items, page, pageSize, total, hasMore }`.
- Services and external modules are classes with **static methods** (carrefour style); nothing is instantiated and no service holds state. Operations scoped to a person take the `user` as an explicit first parameter rather than a constructor argument, so each call site shows what it acts for and permission checks have the subject in hand. Tests spy with `vi.spyOn(Service, 'method')`.
- Services never touch `res`. They return `Entity | null`, arrays, or result unions `{ ok: true, ... } | { ok: false, problem: 'SOME_PROBLEM' }`, with the problem type narrowed to what that method can actually produce (`MembershipResult<MemberActionProblem>`). The controller handler switches over those problems inline, right after the call; there is no shared `sendProblem` helper. A service returns `FORBIDDEN` only for a right that needs more than the caller and the row, such as a player entering their own match result while it has none, or an action on another member that depends on that member's role; every other right is a route middleware (below).
- Every lookup is scoped to what the caller may see (group membership). An unknown or foreign resource answers 404, not 403. 403 (`FORBIDDEN`) is reserved for known-but-not-allowed actions inside a group the caller belongs to.
- A row that a whole family of routes works on is loaded by an `include<Row>` middleware placed after `requireGroupRole` on those routes. `includeTournament` reads `:tournamentId`, looks it up within `req.group` with the relations its handlers need, answers 404 when there is none and sets `req.tournament` (typed with the same `declare global` augmentation as `req.group`). Rows below it, such as an entry or a match, are found in the handler with their own 404.
- A right that the caller and the row decide alone is a `require<Rule>` middleware right after the row's include middleware: `requireTournamentManager` lets only the organiser or an admin through and answers 403 otherwise. The rule itself is an entity method (`tournament.isManagedBy(member)`), which the detail response's `canManage` flag calls too. The route line then states who may call it, as `requireGroupRole` does for group roles, and the handler starts with the rights settled. A route that forgets its rights middleware is open, so every endpoint keeps its 403 test.

## Errors and validation
- Helpers in `utils/ApiResponses.ts`: `sendSuccess`, `sendNoContent` (204, or an empty 201), `sendError(res, code, message, status, details)`, `sendNotFound`, `sendUnauthenticated`, `sendForbidden`, `sendValidationFailed` (422), `sendConflict` (409). Every response leaves through one of these; never call `res.status().json()` or `res.end()` in a controller. The error body is flat `{ code, message, details? }` and `code` comes from `ERROR_CODES`. The frontend translates by code, so `message` is for developers.
- Middleware answers directly instead of throwing. `ErrorHandler` is the last resort: known error classes map to their status, everything else becomes a 500 with details only outside production.
- zod v4 schemas per resource in `app/validators`. `validate()` checks params, query and body at once and reports all issues. The parsed body overwrites `req.body`; parsed query and params are read with `queryOf(req, schema)` and `paramsOf(req, schema)` because Express 5 makes `req.query` read-only.

## Database
- TypeORM active-record entities (`BaseEntity`), `@Entity('snake_table')` with snake_case `name:` on columns, UUID primary keys generated in the app, `datetime(3)` timestamps, `timezone: 'Z'` plus `SET time_zone='+00:00'` on every pooled connection, `decimalTransformer` for DECIMAL columns, `synchronize: false`, entities listed explicitly, and a `toDto()` on each entity.
- Response shapes: every entity that reaches the wire has a `toDto()` for its own columns (and, where other members see a reduced view, a second method such as `User.toSummary()`). Anything that composes an entity with other data (the caller's role, a count, membership state, computed availability) is a static method on a presenter in `app/presenters/<Thing>Presenter.ts` (as in the odido advent backend), so the composition exists once. Services and controllers call presenters; controllers only `sendSuccess`.
- Knex is used only for migrations (`database/migrations/YYYYMMDDHHMMSS_name.ts` with `up` and `down`), run via `tools/migrate.ts` (`latest`, `rollback`, `status`). Migrations are the source of truth for indexes, uniques and ON DELETE rules. New columns use `.after('col')`.
- Query helpers that more than one service needs (`escapeLike`, later pagination helpers) live in `utils/Database.ts`. Counts and other facts about one row (`group.memberCount()`) are methods on the entity, not on a service; a batched variant for lists is a static on the same entity (`Group.memberCounts(ids)`).
- Normalisation of values that are stored, compared or searched (handles, emails) lives in `utils/Normalize.ts` and nowhere else: the zod schema, the blind index, the uniqueness check and the search call the same function. Any new "same value" rule gets a helper there rather than an inline `.trim().toLowerCase()`.
- A pure helper whose result the frontend must reproduce (`slugify` for the invite-link preview, later daypart math) lives in `@bzim/types` (`packages/types/src/text.ts`), not in the API, so both sides run the same code.
- Personal data at rest goes through `utils/Crypt.ts` (`Crypt.encryptColumn()` transformer + a `<col>_hash` blind index via `Crypt.searchHash()` when it must be searchable). Never query an encrypted column directly; add a `findBy<Field>` static on the entity. `APP_KEY` is required at boot.
- Migrations are self-contained: they import only `knex` and Node built-ins, never app code. A migration is frozen history and must produce the same result after the app code moves on (and the test runner loads migrations outside the TypeScript transform, so app imports would not resolve there). Data transformations that mirror a util (such as the `Crypt` payload format) are spelled out inside the migration.
- Time logic (dayparts, "today", current month) uses Luxon in `Europe/Amsterdam` through `utils/Dates.ts`. The database stores UTC.
- Never use the JavaScript `Date` API directly. Wall-clock time is Luxon `DateTime`; elapsed time for timing a job is `process.hrtime.bigint()` (monotonic, unaffected by clock adjustments).
- `DATE` and `TIME` columns are strings on entities (`YYYY-MM-DD`, `HH:mm`): they are wall-clock values with no instant. The data source sets `dateStrings: ['DATE']`; `time` columns use `timeTransformer` from `utils/ColumnTransformers.ts`. Never map them to `Date`.

## Auth and security
- `UserAuth` reads the `access_token` cookie (or `Authorization: Bearer` for tools and tests), verifies the JWT, rejects `type !== 'access'`, and loads the user onto `req.user`. `RequireGroupRole(minRole)` loads the group onto `req.group` and the membership onto `req.membership`; `IncludeTournament` loads the tournament in the path onto `req.tournament`, and `RequireTournamentManager` refuses anybody who may not run it.
- `OriginCheck` runs on cookie-authenticated non-GET requests. `WorkerAuth` (`X-Worker-Token`, `timingSafeEqual`, 503 when unset) guards `/worker/*`.
- A hand-rolled in-memory fixed-window rate limiter with named limits in `ApiLimits.ts` and `resetRateLimits()` for tests.
- Secrets are read lazily in `config/app.ts` (`required()`, `optional()`, `integer()`, `flag()`), so a missing key fails when first used. Keys the app cannot start without are read eagerly.

## Config and environment
- dotenv loads `.env`, or `.env.test` when `NODE_ENV=test`, resolved relative to the config file. `.env.example`, `.env.test.example` and `.env.dist` (placeholders for CI `envsubst`) are committed; real env files are ignored.
- One `env` object is exported from `config/app.ts`, including `isProduction()`.

## Logging and jobs
- Plain `console` with a prefix naming the place (`Calendar connect failed:`, `Unhandled error on POST /api/v1/...:`), `error` for what needs a look and `warn` for what is expected now and then (a tripped limit, a revoke Google refused). No pino or winston, and no logger wrapper: there is nothing to add.
- Nothing personal or secret in a line: an email goes through `maskEmail` and a push endpoint through `shortEndpoint` (`utils/Log.ts`); tokens, keys and cookie values never. Ids are fine.
- Rate limits (`middleware/ApiLimits.ts`): `publicLimit` on every unauthenticated route, `notifyLimit` (60 an hour per person) on what mails a group or its participants, `imageSearchLimit` (20 an hour per person) on the Unsplash search, `mailLimit` and the login limits on auth. A new route that spends an external call or sends to more than one person gets one.
- Scheduled work has no folder of its own. Each cron job is a `POST /api/v1/worker/<job>` endpoint on `WorkerController` (route class `app/routes/groups/worker.ts`) that calls a service method; Ofelia `job-exec` labels run `node dist/tools/worker.js <job>` inside the container, which POSTs to that endpoint. A static in-process flag per endpoint prevents overlapping runs. After a deploy that adds or changes a label: `docker restart scheduler` and check the `job registered` lines.

## Tests
- vitest plus supertest against a real MySQL database whose name ends in `_test` (`tests/support/database.ts` refuses anything else). `globalSetup` runs the Knex migrations once; `setup.ts` connects in `beforeAll`, truncates every table and resets rate limits in `beforeEach`, and disconnects in `afterAll`. `fileParallelism: false`.
- `tests/support/client.ts`: `api = supertest(createApp())`, `asUser(token).get/post/patch/put/delete`, `data<T>(res)` (throws on 4xx/5xx), `error(res)`. `tests/support/factories.ts`: `seedUser()` returning `{ user, accessToken }`, `seedGroup()`, `seedMember()`, `seedActivity()`, `seedLeaderboard()`, all written through entities with `DeepPartial` overrides.
- External providers (Google OAuth, Google Calendar, Brevo) are never called. Tests spy on the factory (`vi.spyOn(CalendarProviderFactory, 'for').mockReturnValue(fixtureProvider)`) or inject `ConsoleMailer`.
- Every backend task ships with integration tests for its endpoints, including the permission denials (404 for non-members, 403 for members without rights).

## Style
- Prettier: 4 spaces, single quotes, semicolons, width 100, trailing commas, LF. ESLint flat config with typescript-eslint `recommendedTypeChecked`; `no-floating-promises`, `no-misused-promises` and `no-explicit-any` are errors; unused vars are prefixed `_`.
- Comments explain why, not what. No em or en dashes in user-facing strings (emails) or code comments.
